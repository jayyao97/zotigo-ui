# Managed Storage and Plain-Folder Adjustment Plan

> Review gate: implementation must not start until a subagent review reports no findings.

This plan amends `project-workspace-session-v2-implementation-plan.md`. Where the two
documents conflict, this document is authoritative.

## 1. Decisions and scope

- Project content managed by Zotigo lives under Electron's macOS `userData` directory:
  `<userData>/projects/<project-id>/`. Project names never determine filesystem identity.
- Project creation does not expose a per-Project location picker. `home_path` remains a
  durable field for ownership checks and future app-level storage migration, but new values
  are generated by Zotigo.
- `knowledge/`, `workspaces/`, Workspace `code/`, `artifacts/`, `notes/`, and Scratch are
  app-managed. The UI exposes Finder actions without presenting those paths as configuration.
- A selected plain folder remains in place and defaults to Direct use. Zotigo does not create
  hidden Git metadata, snapshots, commits, or copies unless the user explicitly chooses them.
- Zotigo may initialize a standard Git repository only after explicit confirmation. Standard
  Git means a normal `.git` entry in the selected folder; no separate or hidden managed Git
  mode is introduced.
- Direct bindings remain durable for the Workspace lifetime in this change. There is no force
  takeover or detach lifecycle yet. A conflict is resolved by reusing the existing Workspace or
  creating a Copy. Git initialization is blocked while any overlapping Direct binding exists.
- Existing Session history is preserved. The authorized cleanup is a one-time local operation for
  the known `zotigo-desktop` Project only, not a product deletion feature. It proceeds only after
  asserting the expected Project id, Source path, zero Workspaces/checkouts/folder bindings, and a
  canonical Home containing exactly three entries: a regular matching ownership marker plus real,
  empty `knowledge/` and `workspaces/` directories. It detaches Conversations, repairs selected
  preferences, records a JSON `pendingManagedHomeCleanup` tombstone in `preferences`, and deletes
  Project/Source metadata in one transaction. Only then is that exact validated Home moved to Trash
  and the tombstone cleared. A Trash failure leaves both a harmless owned orphan and its durable retry
  path/id. Every initial or retried Trash attempt canonicalizes the path again and repeats the exact
  regular-marker/id, exact-three-entry, real-directory, and empty-directory assertions. A mismatch
  retains the tombstone and reports a non-destructive conflict. Any failed assertion aborts cleanup
  without mutation. If the exact tombstoned path is absent on retry, cleanup is terminally complete
  and the tombstone is cleared; a present but invalid replacement retains the conflict. Real Sources
  and their Git metadata are never modified.

## 2. Storage ownership

For a normal macOS development run:

```text
~/Library/Application Support/Zotigo/
├── zotigo-desktop.sqlite3
├── projects/
│   └── <project-id>/
│       ├── .zotigo-project.json
│       ├── knowledge/
│       └── workspaces/
└── scratch/
    └── <conversation-id>/
```

- `electron/main.ts` passes `app.getPath("userData")` into Project and Scratch creation and
  startup repair. Domain services do not independently derive `os.homedir()` defaults.
- New Project Home is exactly `<userData>/projects/<project-id>`.
- New Workspace root is `<project-home>/workspaces/<workspace-id>` and cannot be customized. The user-facing title remains metadata and never affects the managed path.
- All existing marker, real-directory, canonical-containment, crash-repair, and Source identity
  protections continue to apply.
- Existing nonstandard Homes remain readable for compatibility; this change does not silently
  move or delete them. The one authorized local test Home is cleaned separately after validation.

## 3. Source discovery and registration

### Git-aware discovery

Every Git subprocess in discovery, preview, initialization, validation, and worktree provisioning
uses one executor that removes inherited `GIT_*` variables before adding only operation-specific
arguments. This includes directory/index/object overrides and `GIT_CONFIG_*` injection variables.
No call site invokes `git` outside that executor.

Git discovery uses:

```text
git -C <selection> rev-parse --is-inside-work-tree
git -C <selection> rev-parse --show-toplevel
git -C <repo-root> rev-parse --absolute-git-dir
git -C <repo-root> rev-parse --git-common-dir
```

- Exact repository root, linked worktree, submodule checkout, and separate-git-dir checkout are
  Git candidates identified by canonical `git_common_dir`.
- Bare repositories are rejected because they are not editable working directories.
- Selecting a subdirectory of a Git worktree returns an explicit `git_subdirectory` candidate.
  The UI requires one choice: register the repository root or treat only the selected subfolder
  as a plain Direct Source. It never silently promotes or downgrades the selection.
- A failed Git command is treated as a plain folder only when the failure proves the selection is
  outside a worktree. A malformed/broken `.git` entry remains an error.
- A worktree with no resolvable `HEAD` is a `git_unborn` candidate, not a generic error. The UI
  offers `Complete initial commit…`; it never registers the Git Source until `HEAD` resolves.

### Plain-folder default

- `project_folders` gains `default_mode`, constrained to `direct`, `copy`, or `reference` and
  backfilled to `direct`. It also stores nullable `git_context_root` and
  `git_context_common_dir`. Both are null for a folder registered outside Git; both are populated
  only when the user explicitly chooses to treat a selected Git subdirectory as plain.
- Adding a plain folder shows a compact warning before persistence. Direct is the primary action;
  Copy, Initialize Git, and Reference (secondary) are explicit alternatives.
- Registering the same canonical plain folder in multiple Projects is allowed. Registration alone
  does not claim write ownership.

## 4. Standard Git initialization

Fresh initialization and unborn completion share the Direct/topology checks but have distinct Git
preconditions.

Fresh initialization requires that the selected canonical directory:

- is still a real directory;
- is not already inside a Git worktree;
- has no root or nested `.git` entry;
- is not a Zotigo managed Home or Workspace;
- does not overlap any durable Direct binding in any Project or Workspace.

Unborn completion requires that the selection is the exact root of a non-bare repository with no
resolvable `HEAD`. It permits only that root's `.git` entry, rejects nested repositories, repeats the
managed-path and Direct-overlap checks, and never follows a retargeted Git dir.

Git initialization has a durable reservation in `git_initializations`, keyed by canonical Source
path with operation id, initiating Project, root `lstat` device/inode identity, Git-dir identity when
present, phase, and timestamps.
Preview itself is non-mutating and may race. When the user confirms, Zotigo synchronously opens a
`BEGIN IMMEDIATE` transaction, rechecks all overlapping Direct bindings and initialization
reservations, and inserts its reservation before any mutating await. Workspace plan insertion checks
the same reservations in its own `BEGIN IMMEDIATE` transaction. Once reserved, Zotigo recomputes
preview parity and then mutates Git. This closes both ordering races.

The root must remain a non-symlink directory with the same device/inode before every mutating
boundary; same-content replacement at the same path aborts. The reservation phase advances after
ignore write, init, stage, and commit, but phase is advisory. Resume first reconciles actual state:
still-plain resumes fresh validation, an exact-root non-bare repository without `HEAD` resumes unborn
completion, and a repository with `HEAD` skips mutation and finalizes initiating-Project registration.
Any other state is a non-destructive conflict. Startup never deletes reservations by age.

A process-instance id and heartbeat distinguish a live operation from an interrupted one. Cancel is
allowed only for an interrupted owner and transactionally compare-and-swaps operation id/owner before
release; it never removes `.git`, `.gitignore`, or staged content. A live owner must finish or be
aborted/joined by its own process before release, so Workspace creation can never acquire Direct while
Git mutation continues. Concurrent app processes cannot take over a live reservation.

Initialization uses an isolated Git execution profile in addition to the common sanitized executor:

- `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null`;
- an empty `init.templateDir` and `core.hooksPath` created outside the Source;
- `core.fsmonitor=false` for every isolated preview and mutation command;
- `commit.gpgsign=false`;
- no remote command;
- rejection when the effective local config, including `include.path` and matching `includeIf`, contains
  any executable clean/process filter in an existing unborn repository.

The same profile is used for preview, fresh init, add, commit, and unborn completion. Configured
global/system/template/local hooks and commit signing cannot execute or prompt.

The confirmation states that `.git` will be created, no remote/upload is involved, and an initial
local commit will include files accepted by Git and the reviewed ignore rules. It summarizes entry
count, total bytes, files over a conservative large-file threshold, and sensitive-looking names;
it does not display file contents.

### `.gitignore` review

Zotigo never installs a broad language template or overwrites an existing `.gitignore`.

- An existing `.gitignore` must be a regular non-symlink file and is preserved byte-for-byte unless the user explicitly accepts an
  appended, clearly marked `# Added by Zotigo` block. Cancel leaves it unchanged.
- When no `.gitignore` exists, the wizard proposes a reviewable file. The only unconditional
  platform-noise suggestion is `.DS_Store`; there is no automatic `.vscode/`, `.idea/`, `dist/`,
  `build/`, `vendor/`, or wildcard binary rule because those paths may be intentional source.
- Dependency/cache suggestions are based on directories actually present and remain individually
  selectable, for example `node_modules/`, `__pycache__/`, `.pytest_cache/`, `.venv/`, and a
  language-specific `target/` only when the detected project type makes that meaning unambiguous.
- Sensitive-looking names such as `.env`, `.env.*`, `*.pem`, and `*.key` are highlighted. Zotigo
  proposes only the exact detected sensitive paths as positive ignore rules; it does not add broad
  wildcards or negation rules, and it excludes recognized examples such as `.env.example` and
  `.env.sample` from the suggestions. The UI
  explicitly warns that ignored local configuration will not appear automatically in new
  worktrees. Zotigo never copies secrets between worktrees.
- Large files are reported but not silently ignored. The user must choose whether to include them,
  add a reviewed rule, cancel, or configure Git LFS outside this flow.
- Nested `.git` entries are blockers, not ignore suggestions.

For an accurate fresh preview before mutating the selected folder, Zotigo creates a disposable bare Git
dir and a metadata-only mirror outside the Source. The mirror preserves relative path names and copies
only `.gitignore` contents; other files are zero-byte placeholders. Zotigo removes only its uniquely
marked root block in that mirror, asks Git for the baseline NUL-delimited selection using the remaining
standard ignore files, and repeats with the reviewed positive rules. Git remains the ignore-pattern
engine; Zotigo parses only its exact start/end block so crash retry can replace or remove it. Counts and
sizes come from `lstat` on the real Source and never follow symlinks. The disposable probe is removed
after preview. Zero selected user entries is rejected even when the raw folder is non-empty.

The preview records the exact NUL-delimited selected user-path list and the original `.gitignore` bytes,
mode, and identity. Immediately before mutation both are recomputed and must match. Existing
`.gitignore` bytes and identity are revalidated, symlinks (including dangling ones) are rejected,
and the append is an atomic same-directory write preserving the original byte prefix and mode.
Initial creation uses exclusive creation. The Zotigo block has explicit start/end markers and retry
recognizes/replaces that one block rather than appending a duplicate. A mismatch aborts before
`git add` or commit. When Zotigo will create a new `.gitignore`, that generated file is shown
separately and added to the expected commit set; the zero-user-entry check is evaluated before this
artifact is added. After `git add`, the NUL-delimited cached path list must exactly equal the confirmed
user entries plus the explicitly generated/updated `.gitignore` before commit proceeds.

Unborn preview uses the actual isolated/sanitized repository so its root `.git` entry or external
separate Git dir is repository metadata rather than worktree content. It unions NUL-delimited cached
paths with untracked paths selected by standard ignores plus the reviewed positive rule file, and
shows already-staged versus new files separately. Reviewed rules that now exclude an already-staged
path are called out. Zotigo does not silently unstage user work: the user must either deselect the
matching ignore suggestion or unstage the path before continuing. It runs `git add -A` only after the
staged-versus-working-tree state is verified unchanged. Cached parity must match the confirmed union before commit. Root or external
Git metadata can never appear in that union.

After confirmation Zotigo runs, serially for that canonical path:

```text
git init -b main <folder>
git -C <folder> add -A
git -C <folder> -c user.name=Zotigo -c user.email=zotigo@local.invalid \
  commit -m "Initial snapshot created by Zotigo"
```

- An empty folder is rejected with a clear message rather than producing an unborn repository.
- If initialization or commit fails, Zotigo reports the partial standard-Git state and never
  deletes `.git` automatically. Re-entry discovers `git_unborn`, recomputes the preview, requires
  confirmation again, idempotently reuses the marked ignore block, and completes the initial commit.
  It never registers a Git Source before `HEAD` exists.
- On success the Project registers the resulting Git Source. If a plain Source registration for
  the same path in the initiating Project has no Workspace binding, it is replaced transactionally;
  otherwise the Git Source is added alongside it so existing Direct history remains valid.
  Registrations in other Projects are never rewritten; those Projects may explicitly add the new
  Git Source later. On every Workspace submission, plain Sources are re-probed. An exact plain root
  that has become Git is marked unavailable with `unavailable_reason='git_detected'`. A folder that
  is now a Git subdirectory is accepted only when its current canonical repository root/common-dir
  matches the explicit context stored at registration. A previously outside-Git folder whose
  ancestor became Git, or a consented subfolder whose Git identity changed, is marked unavailable
  with `unavailable_reason='git_context_changed'` until the user explicitly reconfirms the subfolder
  treatment. Existing historical bindings remain readable.

## 5. Workspace behavior and Direct conflicts

- Workspace creation keeps Source selection because one Project may contain multiple Sources, but
  it removes the normal Direct/Copy/Reference dropdown. A selected plain Source uses its persisted
  `default_mode`; a conflict-only action may override that one binding to Copy.
- A Project with one available Source preselects it. Multiple Sources render a compact checklist.
- Direct identity is the canonical path snapshot stored on the binding. Active means every durable
  Direct binding whose Workspace has not been deleted; ready/error status does not release it.
  `createManagedWorkspacePlan` uses a synchronous `BEGIN IMMEDIATE` transaction with no awaited
  work: it queries existing bindings, compares paths using component-aware `path.relative`, and
  compares all requested Direct paths pairwise before inserting the requested bindings. Equal,
  ancestor, and descendant overlaps are rejected both against existing bindings and within one plan. The
  existing exact unique index remains defense in depth. A conflict Copy override is part of the
  same submitted plan, so it never relies on the advisory preflight.
- Multiple Sessions in the same Workspace are allowed and share its Direct binding.
- A read-only preflight returns conflict details for UX, while the transactional create boundary
  remains authoritative against races.

Conflict UI:

```text
This folder is edited directly by
Project A / Workspace B

[New session there] [Create a copy] [Cancel]
```

- New session there selects the existing Workspace and opens New Session with it preselected.
- Create a copy retries only the conflicting folder as Copy.
- The UI explains that standard Git initialization is unavailable while the folder is Direct-bound;
  it does not force takeover or race a running Agent.

## 6. UI changes

- Create Project contains Project name and optional Sources only.
- Remove Project Home picker, custom Workspace location input, and ordinary-folder mode dropdown.
- Project Overview replaces the two-row Project Home card with one compact `Managed storage` row
  and Finder action. Shared knowledge is a separate folder action, not a second Home.
- Plain Source rows show their default behavior (`Direct`, `Copy`, or `Reference`) and offer
  `Initialize Git…` where safe.
- Warning and conflict surfaces use the existing compact dark modal/card language, 14px body copy,
  weak borders, 8-12px controls/radii, and no dashboard-style layout.

## 7. Persistence and compatibility

- Add schema migration v4 with a verified pre-migration backup, transaction, integrity check, and
  `project_folders.default_mode` backfill, `project_folders.unavailable_reason`, and the durable
  `project_folders.git_context_root/git_context_common_dir`, plus the durable
  `git_initializations` reservation table.
- Public renderer/preload inputs are typed; Electron main owns filesystem/Git mutation and Zotigo
  storage paths.
- Old v3 `home_path`, `root_path`, and folder binding modes remain readable.
- Source registration and Workspace provisioning remain resumable. Git initialization is not
  rolled back destructively; its partial state is surfaced explicitly.

## 8. Verification

Automated tests use temporary directories only and cover:

- new Home/Scratch locations under a supplied temporary `userData` root;
- no per-Project or per-Workspace custom managed path;
- Git environment variables cannot redirect discovery;
- Git environment variables cannot redirect preview, initialization, or worktree operations;
- linked worktree, separate git dir, Git subdirectory, broken `.git`, and bare repository discovery;
- a consented Git subdirectory remains usable only under the same stored Git context, while a plain
  Source whose ancestor later becomes Git requires explicit reconfirmation;
- plain Source default Direct and explicit Copy/Reference;
- same-path, symlink-alias, ancestor, and descendant Direct conflicts across Projects;
- same-plan ancestor/descendant Direct conflicts;
- multiple Sessions in one Direct Workspace;
- conflict Copy leaves the original unchanged;
- standard Git initialization, `git_unborn` retry, `.gitignore`, initial commit, no remote, empty
  selection, nested Git, exact preservation/appending, sensitive and large-file review, preview
  parity, dangling symlink rejection, retry after ignore append, partial failure reporting, and
  conversion to worktree provisioning;
- initialization/Direct race in both orderings, live/interrupted reservation behavior, and Resume/Cancel;
- injected interruption before/after ignore write, init, stage, commit, and phase persistence; Resume
  reconciles plain, unborn, and already-committed states;
- live Cancel cannot release a reservation to a concurrent Workspace;
- same-content replacement at the reviewed canonical path fails device/inode revalidation;
- unborn retry with staged files and a separate Git dir never previews/stages Git metadata;
- isolated Git config/template/hooks/signing, including a configured post-commit hook that must not run;
- cross-Project conversion changes only the initiating Project's unbound plain registration;
- a plain registration in another Project becomes `git_detected` rather than Direct-binding the new repo;
- v3-to-v4 migration backup, backfill, rollback, and old-path readability;
- cleanup preserves Conversations and never deletes a Source.
- cleanup retry refuses a Home path replaced after the metadata transaction.
- cleanup crash after Trash but before tombstone clearing treats the missing exact path as complete.

Required checks:

```bash
pnpm typecheck
pnpm test
pnpm build
git diff --check
```

Manual E2E uses an isolated Electron `userData` directory and disposable Git/plain folders. It
creates a Project, accepts the Direct warning, creates a Workspace and Session, validates conflict
Copy, initializes a different plain folder as standard Git, and creates a Git worktree Workspace.
At most one minimal LLM turn (`Reply only: OK`) is allowed. The normal Desktop is restarted only
after implementation review reports no findings.
